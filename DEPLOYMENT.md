# Bite Lab auth deployment

The app uses Firebase Authentication, App Check, second-generation Cloud Functions, Firestore for short-lived security state, and Resend for branded account email. The frontend can be published with GitHub Pages or Firebase Hosting. Install the web app with `npm install`; install the Functions dependencies with `npm --prefix functions install`. Run `npm run build` and `npm run test:functions` before deployment.

## Publish the frontend with GitHub Pages

1. Create a GitHub repository and push this project to its `main` branch. This workspace is not currently connected to a Git repository, so it cannot push or publish the files until that is done.
2. In the repository, open **Settings → Pages** and select **GitHub Actions** as the build and deployment source.
3. Add the Firebase web configuration as repository **Variables** under **Settings → Secrets and variables → Actions → Variables**: `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`, and `VITE_FIREBASE_APPCHECK_SITE_KEY`. Also set `VITE_FIREBASE_FUNCTIONS_REGION` to `us-central1` and `VITE_AUTH_FUNCTIONS_BASE_URL` to `https://us-central1-bitelab.cloudfunctions.net` (use the actual deployed Functions URL if its region differs). These are public client settings, not private secrets.
4. Push to `main` or run **Actions → Deploy Bite Lab to GitHub Pages → Run workflow**. The workflow builds and deploys `dist`; it supports both project sites (`https://OWNER.github.io/REPOSITORY/`) and user/organization sites (`https://OWNER.github.io/`).
5. For `kirst3nn/Bitalabtesting`, the Pages URL is `https://kirst3nn.github.io/Bitalabtesting/` and its origin is `https://kirst3nn.github.io`. Add `kirst3nn.github.io` (without protocol or path) under Firebase **Authentication → Settings → Authorized domains** and in the reCAPTCHA/App Check domain allowlists. Set `APP_BASE_URL=https://kirst3nn.github.io/Bitalabtesting` and `ALLOWED_ORIGINS=https://kirst3nn.github.io` for the Functions production parameters, then redeploy Functions. The app base path is needed for reset links; the allowed origin must not include a path. Until this is configured, protected signup/reset requests will be rejected by the backend's origin check.

GitHub Pages hosts the static frontend only. Firebase Authentication, App Check, Firestore, email delivery, and the Cloud Functions backend remain hosted/configured in Firebase. The InfinityFree hostname `bitelab.infinityfreeapp.com` is not automatically connected to GitHub Pages; using it as a custom domain requires DNS control for that hostname.

## Security behavior

- Every account UID is a canonical UUID generated by the trusted Functions backend. The Firebase Auth `beforeUserCreated` blocking function rejects accounts created through any other flow; enable Identity Platform and deploy that function before accepting users.
- Email/password account provisioning is server-side. Google and Apple first link to a temporary UUID account; returning provider accounts are signed in only if their UID is a UUID.
- Registration and reset inputs are normalized and validated on both the client and server. Passwords are never trimmed or rewritten, and are never logged.
- Password-reset links use a random, single-use token stored only as a hash. The backend enforces expiry after **30 minutes** and revokes existing refresh tokens when the password is changed.
- Every HTTP Function requires a valid Firebase App Check token, an exact allowed `Origin`, POST/JSON, and Firestore-backed per-IP/per-account rate limits. CORS is not authentication: direct clients can forge an `Origin`, so App Check and Firebase Auth App Check enforcement are also required.
- Firestore client access is denied. Functions use direct document reads for rate-limit and reset state; the app has no high-traffic Firestore query that needs a composite index.
- Functions write redacted structured logs to Cloud Logging. Passwords, email addresses, reset tokens, App Check tokens, and IP addresses are omitted.

## Firebase and domain setup

1. Create/select a Firebase project and register a Web app. Copy the Firebase public web config values from **Project settings → General → Your apps**.
2. Enable **Email/Password**, **Google**, and **Apple** in **Authentication → Sign-in method**. Complete the provider-specific OAuth setup.
3. Upgrade/enable **Identity Platform** for Firebase Authentication so blocking functions can be deployed. Deploy `enforceUuidAuthUid` before opening signups. This is the backend control that prevents clients or third parties from creating non-UUID Firebase UIDs.
4. In **Authentication → Settings → Authorized domains**, add `localhost`, `127.0.0.1`, and `bitelab.infinityfreeapp.com` (no scheme or port).
5. Register a reCAPTCHA v3 site key for your local and production domains. In **App Check**, register the web app with that key. Put the site key in the Vite environment and configure App Check for Authentication. First monitor valid traffic, then enforce App Check on **Authentication**.
6. Add HTTP referrer restrictions to the Firebase web API key in Google Cloud Console. Restrict it to the local hostnames for development and the exact production HTTPS hostnames after they exist.
7. Configure the Functions production parameters with `APP_BASE_URL=https://bitelab.infinityfreeapp.com` and `ALLOWED_ORIGINS=https://bitelab.infinityfreeapp.com`. These must be exact HTTPS origins with no trailing slash, wildcard, or suffix match. The domain must serve the app over HTTPS with a valid certificate; Firebase Hosting's HTTPS redirect does not apply when the site is served by InfinityFree.

Copy `.env.example` to `.env.local`, then fill in:

```env
VITE_FIREBASE_API_KEY=your-web-api-key
VITE_FIREBASE_AUTH_DOMAIN=your-project-id.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project-id
VITE_FIREBASE_APP_ID=your-web-app-id
VITE_FIREBASE_APPCHECK_SITE_KEY=your-recaptcha-v3-site-key
VITE_FIREBASE_FUNCTIONS_REGION=us-central1
```

These Firebase values and the reCAPTCHA **site key** are public client configuration. Never place a service-account key, Resend key, or rate-limit HMAC key in a `VITE_` variable.

## Resend and Functions configuration

Verify a sending domain with [Resend](https://resend.com/domains) and set its verified sender address. From the project root:

```powershell
firebase login
firebase use --add
npm --prefix functions install
firebase functions:secrets:set RESEND_API_KEY
firebase functions:secrets:set RATE_LIMIT_HMAC_SECRET
```

Enter the Resend API key only at the CLI prompt. Generate a separate random HMAC secret; for example, use Node.js `crypto.randomBytes(32).toString("base64url")`. Do not put either value in source control or chat.

Copy `functions/.env.example` to `functions/.env.<project-id>` and set:

```env
APP_BASE_URL=https://bitelab.infinityfreeapp.com
ALLOWED_ORIGINS=https://bitelab.infinityfreeapp.com
RESEND_FROM_EMAIL=Bite Lab <auth@your-verified-sending-domain>
```

For local emulator use, the example defaults permit only `http://localhost:5173` and `http://127.0.0.1:5173`. Add both only if you use both origins. Keep these development origins out of the deployed production `ALLOWED_ORIGINS`. The production origin must also appear in Firebase Authorized Domains and the reCAPTCHA allowlist.

## Firestore and deployment

Create the Firestore database in the same Firebase project, then deploy rules, indexes/TTL policies, the UUID blocking function, the auth Functions, and Hosting:

```powershell
firebase deploy --only firestore,functions,hosting
```

`firestore.rules` denies all browser reads/writes; Admin SDK Functions bypass client rules. `firestore.indexes.json` defines no query indexes and turns on TTL for the two short-lived collections while disabling unnecessary field indexes. If TTL is not enabled by the Firebase CLI for your project, enable it in Google Cloud Firestore for the `expiresAt` fields in `authRateLimits` and `passwordResetTokens`. Without TTL, expired records remain stored (expired reset tokens are still rejected at use time).

Firebase Hosting automatically redirects HTTP to HTTPS. The Hosting config also sets HSTS and basic security headers.

## Rate limits, logs, and alerts

Current server-side limits are 5 registration requests per IP/hour and 3 per normalized email/hour; 8 new social shells per IP/hour; 5 password-reset requests per IP/hour and 3 per email/hour; 10 reset completions per IP/hour; verification resends have 5 per IP/hour and 3 per account/hour. Firebase Auth also applies its own sign-in protection. Adjust these constants in `functions/index.js` only when usage data justifies it.

Functions structured logs are in **Google Cloud Logging**. Create a log-based metric and alert policy after deployment:

```powershell
gcloud logging metrics create bite_lab_auth_critical_errors --description="Bite Lab auth Function critical failures" --log-filter='resource.type="cloud_run_revision" AND severity>=ERROR AND (jsonPayload.message="auth_request_failed" OR jsonPayload.message="auth_email_delivery_failed" OR jsonPayload.message=~"auth_.*_failed")'
gcloud monitoring channels list
```

Add your verified notification channel resource name to the `notificationChannels` array in `monitoring/critical-auth-errors.json`, then run:

```powershell
gcloud alpha monitoring policies create --policy-from-file=monitoring/critical-auth-errors.json
```

The alert fires when the log metric records a critical auth/email failure during a five-minute window. A notification channel must be supplied to deliver alerts to a person.

## Local test and launch checklist

```powershell
npm install
npm --prefix functions install
npm run test:functions
npm run build
```

Before accepting real signups, configure the Firebase project, Identity Platform blocking function, App Check site key/enforcement, production hostname allowlist, Resend verified sender and secrets, Firestore TTL, and a Monitoring notification channel. Firebase's API key is intentionally public; access is protected by App Check, Firebase Auth, exact backend origin checks, Firebase Auth enforcement, and rate limits—not by hiding the web API key.
